OEM のコピー馬眼力を作るときに、最初に読むファイル。

まずここ 新サーバ手順 今回の施策 書き換える値 テーブル 今の123 cron .env ハマりどころ 直しておきたい所 決定事項

まずここ（5行で）

  1. Laravel が 8（PHP 8.0 で動作中）。OEM で新しい PHP（8.3 / 8.4）を入れるなら、Laravel のバージョンアップが先に必要。ここが一番大きい作業。
  2. サーバの設定（nginx・php-fpm・cron・PM2・Cloudflare）はコードと一緒にコピーされない。このファイルの手順で作り直す。
  3. ドメイン baganriki.com とパス /var/www/horse_odds_finder がコードに直接書かれている所がある。コピー先に合わせて書き換えが必要。
  4. AI の API キー（Anthropic・DeepSeek）はOEM ごとに別にする。費用と利用上限を馬眼力本体と分けるため。
  5. 今回の php2shell 対策（PHP の応急処置）は、新しい PHP を入れるなら不要。ただし「php-fpm で動かす」「PHP を定期的に更新する」は守る。

新サーバを作る手順（この順番で）

  1. サーバ用意：メモリ 4GB 以上（今の123は2GBで、スワップを1.4GB使っている）。OS は CentOS Stream 9 系（AlmaLinux / Rocky でも可）。
  2. SSH を先に固める：鍵ログインのみ・root ログイン禁止（直しておきたい所参照）。
  3. ファイアウォールを有効化：22 / 80 / 443 だけ開ける（今の123は無効のまま）。
  4. スワップ作成：合計 3GB 程度（今の123は /swapfile 1GB＋/swapfile2 2GB）。
  5. MySQL 8.4 を入れる。外部には公開しない。アプリ用ユーザーを作り、root はアプリに使わない。
  6. PHP（php-fpm）を入れる。mod_php（Apache の PHP モジュール）は使わない。拡張は 今の123 の一覧と同じものを入れる。session.upload_progress.enabled = Off も入れておく（害はない）。
  7. php-fpm のプール設定を写す（/etc/php-fpm.d/www.conf）。実行ユーザーは apache、待ち受けは /run/php-fpm/www.sock。
  8. nginx を入れ、/etc/nginx/conf.d/ の4ファイルを写して、ドメインを書き換える（baganriki.conf・horse_odds_finder.conf・php-fpm.conf・cloudflare_realip.conf）。
  9. SSL：certbot（Let's Encrypt）で証明書を取る。自動更新のタイマー（certbot-renew.timer）が動いているか確認。
  10. Node.js（v24）と Playwright を入れる。スクレイパー（scripts/*.mjs の15本）が使う。
  11. Laravel を配置：/var/www/（OEM名）。.env を作り、所有者 centos:apache・権限 640 にする（ハマりどころ①）。
  12. DB を作る：123 からテーブル定義だけ写す（x_____ 付きは除く）。データは過去からの撮り溜め4表だけ本体からもらう（テーブルの分類①）。
  13. PM2 で WebSocket（php artisan websockets:serve --port=8084）を常駐させ、pm2 startup で自動起動にする。
  14. 予測ワーカー（/etc/systemd/system/baganriki-prediction-worker@.service）を写す。
  15. cron を写す（cron 参照）。sudo -u apache が付いている行は外さない（ハマりどころ②）。
  16. Cloudflare：DNS をプロキシ（オレンジ雲）で登録、Service Worker 用の Cache Rule を作る、キャッシュ削除用の API トークンを作る。
  17. Flutter：書き換える値 を直して、deploy.sh の転送先・Zone ID・トークンを OEM 用にしてデプロイ。
  18. 動作確認：トップページ・過去レース画面・プッシュ通知・AI予想（1レースだけ）・429 が出ないか（今回の施策の確認コマンド）。

今回（2026-10-24〜26）入れた施策

「OEM」欄：必須新サーバでも必ずやる　自動コードに入っているのでコピーすれば付いてくる　不要新サーバでは要らない

必須Cloudflare の後ろで、利用者本人の IP を使う

  • ファイル：/etc/nginx/conf.d/cloudflare_realip.conf（サーバ設定なのでコードに含まれない）
  • 理由：これが無いと Laravel から全員が「Cloudflare の IP」に見え、回数制限を他人と共有してしまう。アクセスログも誰のものか分からない。
  • 中身：Cloudflare の IP 一覧（https://www.cloudflare.com/ips-v4 と ips-v6）を set_real_ip_from で並べ、最後に real_ip_header CF-Connecting-IP;
  • 確認：sudo tail -5 /var/log/nginx/access.log の左端が Cloudflare（172.64.・162.159. など）ではなく利用者の IP になっていること。
  • 年1回くらい、Cloudflare の IP 一覧が変わっていないか見比べる。

自動API の回数制限を 60 → 300 回／分

  • ファイル：app/Providers/RouteServiceProvider.php の configureRateLimiting()
  • 理由：トップページ＋過去レース画面で1分60回を超えていた（10/25 は 429 が 1277 件）。
  • 下の2つの施策で呼び出し回数自体を減らしたので、今は余裕がある。

自動過去レース画面：払戻をまとめて取得

  • ファイル：Flutter lib/screens/components/past_race_odds_transition_alert.dart
  • 以前：画面が描き直されるたびに「1日1回 × 全日付（約90日）」を一斉に呼び、失敗すると描き直しでまた呼ぶ（雪だるま式）。
  • 今：開いたら1回だけ、5日分ずつまとめて順番に取得。失敗は最大3回まで再試行。
  • 結果：92回（うち78回が 429）→ 18回（全部成功）。

自動過去レース画面：AI 結果を1日分まとめて取得（新しい API）

  • 新しい API：getHorseOddsFinderAiAnalysisByDate?date=YYYY-MM-DD（HistoryController.php）
  • 以前：日付を開くとレースごとに 1st / 2nd AI を1回ずつ（1日36レースで72回）。しかも保存済みの回答が無いレースでは、その場で有料の AI を呼ぶ作りだった。
  • 今：1日分を1回で返す。保存済みの回答を読むだけで AI は呼ばない。
  • 画面用に整える処理は AiController.php のもの（publicPart・_canReturnSecondAiCache・_loadSavedMergeResult）をそのまま使う。このため3つを public にした（中身は変えていない）。
  • Flutter 側：functions.dart に fetchAiAnalysisByDate / aiByDateKey、path.dart に API 名を追加。
  • 確認：curl -s 'https://（ドメイン）/api/getHorseOddsFinderAiAnalysisByDate?date=（開催日）' でレース数分が返ること。

不要php2shell（CVE-2026-109618 / 109619）の対策

  • 123：PHP を 8.0.30-9 に更新、/etc/php.ini で session.upload_progress.enabled = Off。
  • 新サーバ：修正済みの新しい PHP を入れるので不要。session.upload_progress.enabled = Off は入れておいても害はない。
  • 守ること：PHP は php-fpm で動かす（mod_php は一番危険な構成だった）、PHP は定期的に dnf update 'php*' する。

429 が出ていないかの確認コマンド

sudo awk '$9==429 {print substr($4,2,14)}' /var/log/nginx/access.log | sort | uniq -c

何も出なければ OK。出たら「日付:時」ごとの件数が出る。

ハマりどころ（実際に起きたこと）

  1. .env の権限：centos:apache・640 でないと apache が読めず、全 API が 500（DB ユーザーが forge になる）。.env を触ったら必ず： 
    sudo chgrp apache .env && sudo chmod 640 .env
sudo -u apache test -r .env && echo 読める
  2. AI 補完は apache で動かす：ai-analysis-compensate は sudo -u apache 必須。centos のまま動かすとロックファイルが作れず全レース失敗する（2026-09-28 判明）。
  3. Flutter の更新が反映されない：Service Worker のキャッシュ。nginx で index.html・flutter_service_worker.js を no-cache にし、Cloudflare にも Cache Rule を作る。deploy.sh の最後で Cloudflare のキャッシュを全削除している。
  4. php-fpm の並列数：pm.max_children = 8。利用者が増えると待ちが出る。メモリを増やしたら合わせて増やす。
  5. CentOS Stream のミラーエラー：dnf で「checksum doesn't match」が出ることがある。ミラー側の一時的な不整合で、時間を置くと直る（2026-10-24 に発生、翌日は解消）。
  6. MCP（odds_mysql）の日時：UTC で返るので +9時間して読む。
  7. 毎週土曜 5:50 に全テーブル TRUNCATE：OEM でも同じ設計なら、データの洗い替えを前提に作る。

中storage の権限を 777 → 775（apache グループ）777 は誰でも書き込める
低.env の重複キーを整理どちらが効いているか分かりにくい
