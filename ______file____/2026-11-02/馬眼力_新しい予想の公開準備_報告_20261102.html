馬眼力 新しい予想（v0.4.1-r12.2）を
11/7からお客様の画面に出すための報告

2026-11-02（月）　豊田（作業：Claude）

結論
  1. 11/7（土）から、Flutter web の馬眼力の画面に、新しいプロンプトの予想が出る準備ができました（今の方式とは並走させず、置き換えます）。
  2. 11/2 朝の実AIの試験（東京12R・京都12R の写し）で、両AIとも時間内に返り、決まった頭数（5頭・7頭）を全部公開できました。
  3. 費用は1レース約0.04ドル（1st 約0.015＋2nd 約0.02）。今の方式（約0.08ドル）の約半分です。
  4. そのために、決まりを一部緩めました（帳簿の合わせ直し・頭数の補充・直しの依頼を止める・送り方の変更）。5章の質問に A／B でお答えください。

1. 何が問題だったか（11/2 朝の実AIの試験）

最初は、配布の決まりどおりの検証のままだと、ほとんどの馬が不採用になり、公開できる馬が0〜1頭でした。理由は次の3つです。

  1. 帳簿の合わせ間違いだけで馬ごと不採用：observed_sum／observed_cap の値、非適格馬の rank_basis、公開リストの形（{horse_no,band} で返す）、各馬の public_candidate の印と公開リストのずれ、など。AIの採点・根拠・順位そのものは読めるのに、これだけで落ちていました。
  2. 1st（Claude）が表の形（SOURCE_TABLE_V1）を読み切れない：3回中2回、「参照が足りない」として根拠（evidence）と点数を出しませんでした。2nd（DeepSeek）は同じ形で問題なく読めました。圧縮しないと読めますが、1レース約0.19ドルかかります（送る量が10万トークンを超えて単価が5倍になるため）。
  3. 「考える機能」で時間切れ：2nd（deepseek-flash）は既定で考える機能が入っていて、169秒で時間切れ。1st も考える機能を入れると時間切れでした。

2. 変えたこと

2-1. 帳簿の合わせ直し（決まりを緩めた所）

AIの書いた採点・資格・順位から、決まりで一意に決まる欄だけをサーバが計算し直してから検証します。AIの判断（点数・根拠・順位・資格）は変えません。直した箇所はすべて記録に残します。@ANCHOR-20261102-PREDICTION-CLERICAL（BAGANRIKI_PREDICTION_CLERICAL_FIX=0 で元の厳しい決まりに戻せます）

欄直し方
observed_sum・observed_cap・score_status・total_scorescores から計算し直す（範囲外・整数でない採点があるときは直さず、今までどおり不採用）
非適格馬の rank_basisNOT_RANKED にする
public_candidates{horse_no,band} の形なら馬番の配列にする。さらに「帯の先頭から枠数ぶん、適格馬だけ」の決まりで、AIの順位・資格・role_quota から作り直す（飛ばし取りはしない）
各馬の public_candidate の印・nonselect_reason公開リストに合わせて付け直す。選ばない馬で非選出理由が無ければ、決まったコード（BAND_QUOTA／NO_EVIDENCE／UNVERIFIED）と「サーバが付け直した印」の理由を付ける
shortfalls・validation_issues配列でなければ配列に包む（無ければ []）

直さないもの：根拠が無い、別の馬・当てはまらない統計の参照を根拠にしている、出典が無い、など中身の問題は、今までどおり検証で落とします。

保存済みの返事に当て直した結果（お金をかけずに確認）：1st 表の形 1頭→12頭、1st 圧縮なし 5頭→10頭・10頭→12頭、2nd 圧縮なし 3頭→4頭。

2-2. 決まった頭数を必ずそろえる（補充）

レースの頭数に応じた公開頭数（A・B・D の枠）を必ず出します。@ANCHOR-20261102-PREDICTION-FILL

  1. 検証を通った馬で足りなければ、足りない分を、同じ人気帯の中でAIが付けた順位（band_ranks）、無ければ6分前の人気順で補います。
  2. 帯に馬がいなければ、D の不足は B から、B の不足は D から、A の不足は B→D の順で取ります（公開の不足の埋め方と同じ順）。
  3. 補った馬は、おすすめ度を付けず（0）、選出理由に「補充：AIの根拠を確かめきれなかったため…」と書きます。
  4. 公開の締切までに検証を終えられなかったレースも、凍結した出走馬から、この補い方で頭数をそろえて出します。

補充は画面に出すときだけで、baganriki_publications（公開の記録）は契約どおりのまま変えていません。

2-3. 送り方（入力の圧縮）

  • 1st：SOURCE_DICT_V3（出典の名前 source_ref で値を引ける辞書の形。項目名を短くし、source_ref から一意に分かる値と、項目ごとに一番多い値を省く）。BAGANRIKI_R122_COMPACT_1ST=dict3
  • 2nd：SOURCE_TABLE_V1（10/23 に合意した表の形のまま）。BAGANRIKI_R122_COMPACT_2ND=1
  • どちらも、詰めたあと必ず元へ戻して、凍結入力と1バイトでも違えば詰めずに元のまま送ります。7レース分の凍結入力で、元に戻ることを確認しました。
  • 凍結入力（snapshot_hash の元）と検証は元のままです。変えるのは送る文字列だけです。

1st に足す説明文（SOURCE_DICT_V3_ADDENDUM_V1・sha256 accadf3a…e1f9）：

【送信形式 SOURCE_DICT_V3】
この入力では source_registry を source_dict に詰めて送る。中身は source_registry と同じで、値・出典は1件も省いていない。
source_dict.entries のキーが source_ref で、値がその出典1件。各馬の値は h{馬番}_{field}（時点があれば _{分前}）のキーで引ける。
各件の項目名は短くしてある：v=value、f=field、h=horse_nos、ah=applicable_horse_nos、p=parents、s=slot_offset、o=observed_at、a=available_at、c=computed_at、d=dependency_key。
f が無ければ、source_ref から先頭の「h{馬番}_」と末尾の「_{s}」を除いた残りが field。
h が無ければ、source_ref が h{馬番}_ で始まるなら [馬番]、それ以外は []。ah・p が無ければ []。s・c が無ければ null。
o・a・c は source_dict.time_dict の番号（0始まり）。o が無ければ source_dict.field_auto[field].os[s]（s があるとき）、無ければ field_auto[field].o、それも無ければ null。a が無ければ field_auto[field].as[s]（s があるとき）、無ければその件の o と同じ。
d が整数 n なら source_ref の先頭 n 文字。d が無ければ source_dict.field_auto[field].d（{h} は馬番）、それも無ければ source_ref と同じ。
race_id は全件 source_dict.race_id。unit・dependency_role・source_kind・scope・formula_id・formula_version は、その件にあればその値、無ければ source_dict.field_defaults[field] の値。
field_catalog の各項目で、display_label が無ければ項目名と同じ、maximum・minimum が無ければ null、missing_allowed が無ければ true。
input_indices は送らない（source_dict から用途別に引ける）。coverage の source_fields は、その field の出典すべてを指す。
根拠を引用するときは entries のキー（source_ref）の文字列をそのまま使い、facts の value にはその件の v をそのまま書く。source_registry と書かれている指示は source_dict に読み替える。

2nd に足す説明文（SOURCE_TABLE_V1_ADDENDUM_V2・sha256 459bdb08…d1a4。10/23 版のまま）：

【送信形式 SOURCE_TABLE_V1】
この入力では source_registry を source_table に詰めて送る。中身は source_registry と同じで、値・出典は1件も省いていない。
source_table.rows の1行が出典1件。各行の値の並びは source_table.columns の並びと同じ。
race_id は全件 source_table.race_id。
observed_at・available_at・computed_at の値が整数なら source_table.time_dict の番号（0始まり）。null は null のまま。
unit・dependency_role・source_kind・scope・formula_id・formula_version は、columns にその項目があれば、その行の値を使う（null も行の値として扱い、field_defaults で置き換えない）。columns に無い項目だけ source_table.field_defaults[field] の値を使う。
dependency_key は、null なら source_ref と同じ、整数 n なら source_ref の先頭 n 文字、文字列ならその文字列。
parents の要素は、整数なら rows の行番号（0始まり）の source_ref、文字列ならその名前のまま。
input_indices は送らない（source_table から用途別に引ける）。coverage の source_fields は、その field の出典すべてを指す。
根拠を引用するときは rows にある source_ref の文字列をそのまま使う。source_registry と書かれている指示は source_table に読み替える。

2-4. そのほか

  1. 直しの依頼（訂正）を止める：BAGANRIKI_R122_FIX_POLICY=never。11/2 の試験で、1st は2回とも「この出力は私が生成したものではない」と答えを断り、2nd は直してはいけない馬まで変えてきて不採用でした。費用と時間だけかかるので止めます（契約の「最大1回」の範囲内）。
  2. 2nd の考える機能を切る：BAGANRIKI_R122_2ND_THINKING=disabled。切ると70〜85秒で返ります。
  3. 今の画面の取得口から新しい予想を返す：アプリの改修なしで、getHorseOddsFinderAiAnalysis（1st）・getHorseOddsFinderSecondAiOpinion（統合結果 merged_horses）・1日分の取得口が、対象レースでは新しい予想を今と同じ形で返します。旧方式のAIは呼びません（再読込み・「AI予想」ボタンでも呼ばない）。BAGANRIKI_PREDICTION_PUBLIC=1 のときだけ。
  4. 選出理由は決まった形の文：AIの文章（explanation）は検証なしで出さない決まりなので使いません。凍結した入力の値と、サーバが確かめた根拠の系統だけで作ります。例：
    確かめた根拠：オッズの動き、能力と適性（2系統）。6分前の単勝 3.4倍（21分前 3.8倍）。複勝 1.5〜1.8倍。近3走 3着・4着・5着。
  5. おすすめ度：統合点（0〜100、両AIの公開候補の加点+5を含む）を四捨五入して100で止めます。購入推奨の印は出しません（buy_recommended=false のまま）。波乱度などのレース指標は新しい予想に無いので出しません。
  6. 凍結できなかったレース：凍結の時刻（発走5分30秒前）から30秒たっても凍結入力が無く、発走3分前より前で、予算が足りるときだけ、1回だけ今の方式に切り替えます（切り替えたレースは新しい予想を送らない）。
  7. 費用の歯止め：1日の予算 4ドル（見込み 約1.5ドル）。TARGETS=ALL は1件と数えられて12レースの上限が効かなかったので、ALL は予算を書いたときだけ効くようにしました。予算には、圧縮した送信・しなかった送信・今の方式への切り替えを全部数えます。
  8. 6分前オッズの取得が遅れて10/31 に凍結が24レース中22レースで失敗した件：取込コマンド（ImportKeibaOdds）の待ち方を直し、11/2 にサーバへ反映済みです。11/1 は設定の読み込みの不具合で 2nd が全レース 401 でした（11/2 朝に直しました）。
