# ⑤ 投票締切（sales_close_at）の正本 ─ 調査と具体案

作成：2026年10月20日（JST）

---

## 1. 現状

既存DBに投票締切の値はありません。

* `t_horse_odds_finder_races` にあるのは `start_time`（発走時刻）だけです。
* データベース全45テーブルの列名を確認しましたが、
  締切・発売終了・sales・close に当たる列はありません。

したがって `publish_deadline = sales_close_at − 60秒` が計算できません。
契約11.2「正本が特定できないレースは公開しない」に従い、
**正本が決まるまで公開は開始しません**。

なお前回「一定秒数を引くことは全面禁止」と書いたのは、こちらの理解が広すぎました。
仕様は「**根拠なく**一定秒数を引かない」です。訂正します。
この確認で特定の秒数や取得元が承認されたとも受け取っていません。

---

## 2. 取得元の候補（3案）

### A案　既存の取得経路に締切を足す

いまオッズと出馬表を取っている経路に、締切の項目があるかを調べ、
あれば `races` へ列を1本足して取り込みます。

* 調査 … 0.5日
* 実装 … 0.5日（取得処理の改修とテーブル列の追加）
* 長所 … 取得経路が1本で済み、前倒しも同じ経路で拾える見込み
* 短所 … 取得元に締切が無ければ使えない

### B案　別の公式情報から取る

締切を別途取得し、レース識別子で突き合わせます。

* 実装 … 1〜1.5日（取得・突き合わせ・前倒しの反映）
* 長所 … 取得元を明示できる
* 短所 … 経路が増える。取得失敗時の扱いを決める必要がある

### C案　規則として定義する

公式情報と適用条件を確認したうえで、
「発走時刻から○秒前」を**根拠つきの規則**として正本に据えます。

* 実装 … 0.5日
* 長所 … いちばん早い
* 短所 … **定義と検証方法の明記が必要**で、ご承認が要ります。
  根拠が示せないならこの案は採れません。

---

## 3. どの案でも必要になること

| 項目 | 内容 |
| --- | --- |
| 正本の定義 | どの情報を正本とするか、どの時点の値か |
| 取得時刻 | いつ取得した値か（監査に残す） |
| 前倒しの反映 | 締切が早まったときに `live_close` へ入れる経路 |
| 延長の扱い | 延長では猶予を増やさない（契約どおり） |
| 取得できない場合 | そのレースは公開しない。理由コードを返す |
| 検証方法 | 正本と実際の締切が一致することをどう確かめるか |

---

## 4. こちらからのお願い

**まずA案の調査（0.5日）をさせてください。**
いまの取得経路に締切の項目があるかどうかで、採れる案が決まります。

調査の結果をお出ししたうえで、A・B・Cのどれにするかをご判断ください。
C案を採る場合は、根拠とする公式情報と適用条件をご指定ください。

---

## 5. 当面の進め方

投票締切が決まるまでの間も、次は並行して進められます。

* 取得時刻の記録（お願い②のA案・承認済み）
* 採用バッチの選定の本番接続
* 凍結入力の保存

これらは締切に依存しません。
実AIの接続試験が必要になった場合は、ご指定のとおり
**試験用の時刻を別IDでREPLAYへ隔離**し、本番の正本へ混ぜません。
実取得の監査記録は、AI試験とは分けて先行します。
