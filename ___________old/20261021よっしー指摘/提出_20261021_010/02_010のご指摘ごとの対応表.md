## 2. Job構成（010の2章）

### 2-1 databaseでもworkerは必要／秒数の整合

待ち行列を4本に分けました。

| 待ち行列 | 役 | 枠 |
|---|---|---|
| `r122-freeze` | 入力凍結 | 1 |
| `r122-ai-1st` | 1st のAI待ち | 2 |
| `r122-ai-2nd` | 2nd のAI待ち | 2 |
| `r122-agg` | 期限判定・統合・公開・実状態 | 1 |

1st が145秒かかっていても、2nd と期限処理は止まりません。

秒数は、入力凍結（T−330）から応答期限（T−150）までの **180秒**の内側に
収めました。1本の `RunRoleJob` に初回と訂正の両方を入れています
（分けると待ち行列をもう一度通るので180秒では間に合いません）。

| 値 | 秒 | 根拠 |
|---|---|---|
| AnthropicService の HTTP 上限 | 120 | private const を**リフレクションで実測**（書き写していません） |
| RunRoleJob の上限 | 175 | 180秒の窓の内側。HTTP 上限より長い |
| worker の `--timeout` | 180 | Job の上限以上 |
| 接続の `retry_after` | 300 | worker の上限より十分長い |

`RunRoleJob` は **`$tries = 1`** です。やり直すと外部APIへ二度送るためです。
worker が落ちて同じJobがもう一度動いたときは、`r122SendFirst` が
「その role の初回の枠はすでにあります」で何もせず返ります。
これが「worker再実行と外部API再送の区別」です。

`ShouldBeUnique` は**使いません**。鍵が cache driver（この環境では file）に
乗るので、本物の見張りとしては弱いためです。二重の見張りは、すでにある
一意制約（枠・凍結入力）に任せます。

試験：`--r122-job-test` の J-06〜J-15。

### 2-2 4本の役割

| Job | やること | やらないこと |
|---|---|---|
| `R122FreezeRaceJob` | 既存の凍結処理を通し、保存成功後に 1st と 2nd を独立に投入。応答期限に連動する集計も予約 | 凍結後に馬データを取り直さない |
| `R122RunRoleJob` | `r122SendFirst` **だけ**を呼ぶ。検証→訂正→採否はその中の `r122AfterReceive` が1回ずつ行う | **公開はしない**（集計Jobへ渡す）。後処理を二度呼ばない |
| `R122AggregateRaceJob` | AIを待たず、保存済みの結果で公開判定。受領時と期限時の2つの起動を持つ | 外部へ1回も通信しない |
| `R122UpdateRaceLiveJob` | 実状態（取消・締切の前倒し）を既存の版管理へ。再判定を起動 | AIへ送らない。凍結済み本文を触らない |

「未commitのsnapshotをworkerが先に読まない」は、接続に
`'after_commit' => true` を入れて担保しました。
試験 J-24a で「commit前は jobs 表に入らない」ことを確かめています。

`r122AfterReceive` 末尾の直接公開は、Jobの段が上がっているときだけ
**採否確定の印を残して集計Jobへ渡す**形に変えました。
段が下りているときは今までどおりその場で公開判定まで進みます。

試験：J-20〜J-34、J-35〜J-46。

### 2-3 dispatchする入口

| 入口 | いま |
|---|---|
| 通常アクセス・`r122AfterCached` | `r122DispatchForRace` を呼ぶだけ。**terminating 内でAIを待ちません** |
| `r122SweepPending` | 発見・投入漏れの回復・期限判定・集計の起動だけ。`r122SendFirst`／`r122SendFix` を同期実行しません |
| 対象レースの定期起動 | 凍結が無ければ `FreezeRaceJob` を積むので、snapshot 未作成のレースも拾えます |
| 凍結完了時 | 応答期限に連動する集計Jobを独立に予約（**期限ぴったりと3秒後の2回**） |
| 期限の回復処理 | AI応答待ちと独立。`$now > reply` を **`>=`** に直し、期限ぴったりの1回で待ちに終わらないようにしました |

試験：J-32〜J-34、X-23b。

### 2-4 並列化で新たに注意が必要な「早すぎる公開」

**ご指摘のとおりでした。** いまの数え方は「HTTPが返った」までしか
見ていませんでした。2つを分けました。

| | 何を表すか | どこに在るか |
|---|---|---|
| 受領の終端 | HTTPが返った（または失敗が確定した）だけ | `baganriki_ai_attempts.status` が TERMINAL |
| **採否の確定** | 診断→必要な訂正→採否まで終わった | `baganriki_audit_events` の `kind='R122_ROLE_SETTLED'` |

印は「snapshot・role・**応答の版**」と結び付けます。版は、その role の
初回と訂正の `(attempt_no, status, response_hash, complete)` から作る
SHA-256 です。印を付けたあとに訂正が届けば版が変わり、印は効かなくなって
もう一度待ちに戻ります。**新しい表は作っていません。**

あわせて1つ、こちらで足りないところが見つかりました。
初回が FAILED／UNKNOWN_RESULT で終わった役には、診断も訂正も採否も
やることが残っていません。印は受領に成功したときだけ付くので、
待っても永久に付きません。ここで待たせると、失敗した役のぶんだけ
公開が応答期限まで遅れます（公開期限は応答期限の30秒後しかありません）。
「採るものが無い」ことを確定として数えるようにしました。
**RECEIVED のときは数えません。** それが2-4のご指摘です。

試験：X-22b〜X-22i（印なしでは公開しない／版が変われば待ちへ戻る）、
E-11-1〜E-11-3、E-19-0〜E-19-1、E-37-0〜E-37-2。

### 2-5 切替・重複・検証対象

**経路の固定**：レースの処理開始時に JOB／SYNC を監査へ記録し、
**上書きしません**。旧経路で始まったレースにJobから触りません。
Job失敗を理由に旧経路から再送もしません。試験 J-20〜J-23、J-34。

**12レース限定**：判定は1つの関数（`r122TargetCheck`）です。
**書き写していません。** 見る場所は5か所です。

1. `r122SendFirst`（初回の送信許可の直前）
2. `r122SendFix`（訂正の送信許可の直前）
3. `r122SweepPending`（巡回）
4. `r122AfterCached`（キャッシュ後）
5. `R122RunRoleJob`（待ち行列から出たとき。積まれてから時間が経つため）

`BAGANRIKI_R122_TARGETS` が**空のときは1レースも送りません**。
「指定が無ければ全部送る」の逆にしています。設定を入れ忘れた日に
全レースへ送るほうが危ないからです。

試験：J-17〜J-19（判定そのもの）、J-47〜J-52（入口に呼び出しが在ること）。

## 3. 型保持（010の3章）

### 3-1 設計Aには賛成。ただし提示されたクラスだけでは完成しない

**ご指摘のとおりでした。** `r122SaveValidation` が通常の `json_encode` の
ままだったので、クラスを足しても解消しません。

専用シリアライザ `BaganrikiJson::encode($値, $地図)` を作り、
`r122SaveValidation` をこれに替えました。数値だった経路は
**原トークンのまま引用符なし**で書きます。
`JSON_NUMERIC_CHECK` も float への変換も使っていません。

**なぜ「全部を値オブジェクトで包む」形にしなかったか。**
すべての値を包むと、既存の業務の判定（`is_int`・`array_sum`・`foreach`・
比較演算）が全部落ちます。ご指摘にもあるとおり「全部包むが is_int は
そのまま」では正しい整数まで落ちます。
採ったのは、値はPHPの素の値で持ち、**型は経路をキーにした地図で並べて
持つ**形です。

```
map['num'][経路]  = ['raw','decimal','exact','form']
map['kind'][経路] = 'obj' | 'arr'
```

業務の判定は素の値でそのまま動き、型が必要な場所（比較・保存・読戻し）
だけが地図を見ます。値を包まないので「**同じ値の別インスタンス**」問題も
起きません。値オブジェクト（`BaganrikiDecimal`）は1つの値を持ち回す
入れ物として残します。地図はその全体版です。

**「監査5,000件制限との分離」も、本物の不具合でした。**
丸まる数値の置き替え（inexact）には上限が無いのに、型の地図を監査と
同じ 5,000 で切っていました。5,001個目から先は「文字列に置き替わったのに
数値だった印が地図に無い」状態になり、再保存で**数値が文字列へ化けます**。
3-5の「5,001個目の長い数値」がこれでした。

| | 上限 |
|---|---|
| `numbers`（監査の一覧） | 5,000 件のまま |
| `number_paths`（型の地図） | 200,000 件 |
| `kind_paths`（obj/arr の地図） | 200,000 件 |

試験：T-29〜T-34。

### 3-2 比較はBを選びます

`BaganrikiJson::same($a,$地図A,$b,$地図B)` が次を見ます。

- JSON上の型（数値／文字列／真偽／null／obj／arr）
- 数値は**正確な十進値**と、**表記**（int／dec／exp）
- obj は**キーの集合（順序は無視）**
- arr は**長さと順序**

`sameHorseRow` と、訂正対象外フィールドの比較をこれに替えました
（地図が無いときは従来どおり `===` です）。

PHPの `===` で**見逃していたもの**を、同じ材料で並べて出します。

| 変更 | `===` | 地図あり |
|---|---|---|
| `2e0` → `2.0` | 同じに見える（どちらも float 2.0） | **別物** |
| `{}` → `[]` | 同じに見える（どちらも空配列） | **別物** |
| `1.999…`（数値）→ `"1.999…"`（文字列） | 同じに見える（どちらもPHP文字列） | **別物** |

末尾の0（`1.50` と `1.5`）は**同じ**と見ます。十進値も表記（dec）も
同じで、値も型も変わっていないためです。保存では原トークンをそのまま
書くので `1.50` は `1.50` のまま残ります。

試験：T-01〜T-24、T-38〜T-42、P-06〜P-17。

### 3-3 整数検査と保存後の読戻し

整数は PHP の `int` のまま残るので `is_int` がそのまま効きます。
`1.0` と `1e0` は `float` なので、整数必須の検査が落とせます。
`1` / `1.0` / `1e0` は比較で別物です。

読戻しも専用パーサに統一しました（`r122NormalPart`）。
**通常の `json_decode` は使いません。** `r122NormalRoundTrip` で
「保存 → 読戻し」が型も値も一致することを確かめます。

試験：T-07〜T-16、P-22〜P-30。

### 3-4 空オブジェクトだけでは不十分

**ご指摘のとおりでした。** 経路ごとに obj／arr を控えるようにしました。
空かどうかに関係なく、`{"0":"a","1":"b"}` と `["a","b"]` も区別します。

並べ替えには `mapMove`／`mapMerge` で地図を追従させます。
normal は馬番キーのオブジェクトなので、各馬の枝を
`["horses",3]` から `["7"]` へ付け替えています。

試験：T-17〜T-24、T-25〜T-28、P-14〜P-15。

### 3-5 最低限確認する例

6例すべてを、**extract だけで終わらせず**、本番の関数で
診断→訂正比較→保存→読戻しまで通しました。

| ご指摘の例 | 試験 |
|---|---|
| 数値 1.99999999999999999999 と、同じ内容の文字列 | T-01〜T-06 |
| 整数1、小数1.0、指数1e0 と、整数必須フィールドの判定 | T-07〜T-16 |
| []、{}、数値キーを持つオブジェクト | T-17〜T-24 |
| 馬行の並べ替え、値を変更した後の保存 | T-25〜T-28／P-18〜P-21 |
| 5,001個目の長い数値 | T-29〜T-34／P-26〜P-30 |
| 同じ値の別インスタンスを使った正常な訂正 | T-35〜T-37／P-18〜P-20 |

P群は `r122InspectResponse`／`r122AcceptedHorses`／`r122SaveValidation`／
`r122NormalPart` を実際に呼んでいます。
