### 11/14（土）の追加：来週の作業の3つ目（よっしーさんの判断・なるさんの整理）

- **頭数どおりに馬を出す**（枠が埋まらないときの扱い）：**B「頭数分を表示し、自信のある馬から並べる」**。なるさんの「来週の改修順序と選出頭数復元案（11/14）」に沿って進める。

- **通常候補**：1stか2ndの**少なくとも片方**で、今の基準を満たす根拠を確かめられた馬（両AIの一致は必須にしない。一致の加点は今の決まりのまま）。
- **選び方の順番**：先に人気帯ごとの枠と検証済みの順位で「選ぶ馬」を決め、その後で表示の順を整える。おすすめ度の順に選び直して穴の枠を失うことはしない。おすすめ度が比べられないときは、検証済みの根拠の順位・統合の順位を使う。新しい点数は作らない。
- **補充**：通常候補で埋まらない枠だけを、同じ人気帯の中で補う。使える検証済みの順位があればそれを、無ければ凍結した6分前の人気順を使う。後ろに並べて「補充」と書き、おすすめ度は付けない。根拠・点数・期待値を作り足さない。購入推奨に自動で入れない。帯に馬がいないときの枠の移動は今の決まりのまま。評価の後にB・Dが足りないことを、無条件にAで埋めない。
- **記録**：「通常候補だけで頭数どおり」「補充を含めて頭数どおり」「AIの評価が成り立たず参考表示」「データ不足で表示できない」を分けて記録し、同じ成功として数えない。回収率も、通常候補だけ・補充だけ・表示全体を分けて残す。AIの評価が全体で成り立たなかったときは、その旨を表示する。
- **まず原因を分ける**：11/14の7レース（福島3R 4/7、福島6R 5/6、東京6R 0/6、京都7R 0/7、福島8R 1/7、東京8R 1/5、福島11R 3/7）について、両AIの有効な評価頭数、帯ごとの適格数、統合後の通常候補数、不足の理由、補充数、表示数を並べる。0〜1頭を「補充をやめたから」と決めつけない。根拠のある馬を不当に落とす不具合があれば、そこを直す。
- **確かめること**：8/9・13/14・15/16頭の境目で頭数が切り替わる／いない帯・評価後の不足・取消を区別する／同じ馬・取消馬・別レースの馬を補充しない／通常と補充の区分が記録・画面・成績で一致する／表示順を変えても選ぶ馬の集まりは変わらない。コメントアウトした処理を戻すだけで終わりにしない。

### 11/14（土）の追加：来週の作業の4つ目（なるさんの依頼）

- **波乱度・下位侵入度・大穴侵入度が出ない件の、原因調査と修正**。
- **目指す状態**：材料がそろい、今の算出条件を満たすときは、正しく算出して画面に出す。本当に資料が足りないときは「未算出」のまま。人気帯そのものがいないときは「対象外」と分ける。数字を出すためだけに、0や決まった値で埋めない。
- **11/14の実際（読み取りで数えた値）**：公開32レースのうち、3つとも出た11、一部だけ出た12、3つとも出なかった9。出なかった理由は「AIが値を返したがサーバの検査で外された（INVALID）」と「AIが値を返さなかった（UNKNOWN）」の2種類がある（例：東京4RはAIが3つとも値を返したが、3つとも外れた）。
- **調べる箇所**：同じレース・同じ凍結入力で、入力 → AIの回答 → 検査 → 保存 → アプリへの返却 → 画面表示を追い、どこで未算出になったかを分ける。
  - 必要な時系列オッズや人気帯の情報が、実際に入力に入っているか
  - 材料があるのに、AIが「資料不足」として返していないか
  - AIの値が検査で外されていないか。その判定は正しいか
  - 正しい値が保存されているのに、返却や画面の対応で未算出になっていないか
  - 片方のAIだけで公開したとき、3指標を出す側（1st）の結果がどう扱われているか
- **直し方**：指標の意味と算出の基準は変えず、原因が分かった箇所だけを直す。「資料不足」「対象帯なし」「AI未評価」「検査不合格」「保存・表示の不具合」を同じ原因として扱わない。補充の馬を足しただけで、指標まで出た扱いにはしない。人気帯の枠やE3・E5の式は変えない。
- **確かめ方**：同じレースで、指標ごとに修正前後の値・未算出の理由・画面表示を比べる。報告には、対象レース数と、指標ごとの「出せた件数／未算出の件数と理由／対象外の件数」を書く。AIの返事が届いたことと、正しい指標を表示できたことは分けて数える。

## 3. 作業A：古いデータの読み取り調査（③）

**DBを読むだけ。本番には一切書き込まない。AIへの送信も無い（0円）。**

### A-1. 使えるデータが、いつから・どれだけあるか

E3・E5の過去レース（P）に必要なものを、10/24 より前について1つずつ数える。

| 必要なもの | 中身 | 調べる場所（候補） |
|---|---|---|
| 6分前の単勝オッズ（全頭） | 式の順位 r・断層 q・D² の②に使う | オッズの保存テーブル・保存ファイル |
| 21分前の単勝オッズ（全頭） | 変化 m（D² の③）に使う | 同上 |
| 馬の対応 | 6分前と21分前を同じ馬で結ぶ（馬ID・馬番） | 出馬表・オッズの行 |
| 確定着順（全頭） | B(k,r)・A(k,i) に使う。同着を正しく数える | `t_horse_odds_finder_race_result_history` |
| 頭数・馬場種別・距離・クラス | P の選び方と D² の④⑤に使う | レース表・結果表 |
| 公式結果が利用可能になった時刻 | 「対象日の JST 午前0時より前」の判定に使う | 結果表 |

### A-2. 不足の理由を数える

レースごとに、使えない理由を1つずつ記録して数える。

- 6分前オッズが無い／一部の馬だけ欠けている
- 21分前オッズが無い／馬の対応がとれない
- 確定着順が無い・数字でない・矛盾している
- 馬場種別が平地でない（障害など）
- クラスが不明（特別レースなど。レース表に class の列が無い件を含む）

### A-3. 試算表の M＝205 の出どころ

`t_horse_odds_finder_expected_score.m` がどの過去レースを数えているのかを、本番の `expectedHistory` の集め方と並べて比べ、違いを書き出す。

### A-4. 終わったレースを確かめるときの決まり

- 対象レースの日より後の結果を混ぜない（P は「対象日の JST 午前0時より前に公式結果が利用可能」なものだけ）。
- 古いデータを足して作り直す場合も、凍結済みの過去のレースの入力（snapshot）は書き換えない。

### A-5. 出すもの

- 頭数×馬場種別ごとの「使える過去レース数」の表（今の数と、古いデータを足した場合の数）
- 使えない理由ごとの件数
- 11/7・11/8 の998頭について、古いデータを足した場合に COMPARISON_READY になる馬の数（読み取りだけで計算した試算。本番には入れない）
- M＝205 の出どころの説明
