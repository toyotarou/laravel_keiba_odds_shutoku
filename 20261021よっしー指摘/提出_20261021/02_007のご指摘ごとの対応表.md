## 7章　厳密JSONは構文検査が増えたが、正確な数値保持は未達

**ご指摘のとおりでした。しかも、一度直し方を間違えました。**

最初は「PHPで正確に持てない数値は受け取らない」という検査を入れました。ところがこれは、**契約9章が許している有効桁128桁の数値まで拒否します。** 128桁は倍精度では必ず丸まるので、正しい応答を落とす側の誤りでした。自分の試験（有効桁128はちょうど通る）が落ちて気づきました。

ご指摘の文は「許容された数学的有限数を INF や丸めた別値へ変えないこと」「数値トークンの原表現と型を保持し、必要な任意精度計算へ渡してください」です。**拒否ではなく保持**が筋ですので、方針ごと差し替えました。

| 応答に来た数値 | いまの扱い |
|---|---|
| `11` / `2.5` | そのまま数値。変えません |
| `1.99999999999999999999` | 通す → `'1.99999999999999999999'`（原表現の文字列） |
| `12345678901234567890` | 通す → `'12345678901234567890'`（原表現の文字列） |
| `2e308` | 通す → 309桁の十進数。**INF にしません** |
| 有効桁128 | 通す → 原表現のまま |
| 有効桁129 | 拒否（契約の上限） |

置き替えるのは数値トークンの位置だけなので、本文の他の部分は1バイトも動きません。混在していても、丸まらない数は数値のままです。

**「AIが返した数値文字列を勝手に数値として通す変更もしないでください」**という点については、型は後段で見ます。採点は整数と決まっているので、丸まる数が採点に来れば文字列のままになり、採点の検査（`is_int`）が落とします。その条件が診断に入っていること自体も試験で見張っています。

### 算出時刻が永久に入らない作りでした

の2つが別々に読めます。どちらも事実です。平均の値は元データだけで決まるので、同じ元データならいつ計算しても同じ値になります。
